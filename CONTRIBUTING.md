# Working on BLAKE3 servil

## Servil Software Factory: values, goals, and principles

**We aspire to create software that serves its users reliably and loyally.** That is easy to say and hard to do. [The Servil Software Factory's page](https://github.com/servil-software-factory) says how we do it: the practices its projects share, which projects it supports (from version 1.0; this one is the first candidate), and what a project needs before it is supported. Five principles govern every change here:

1. **Loyalty to the user:** minimize what the user has to trust — small owned code over sprawling dependency trees, hash-verified build inputs, and byte-for-byte reproducible releases.
2. **Reliability by construction:** make invalid states unrepresentable, keep critical invariant checks active in release builds, fail closed, prove critical kernels, and test the tests with mutation testing and planted faults.
3. **Radical honesty:** document what every check covers *and* what remains outside it (`QUALITY.md`), disclose AI authorship and lack of independent human audits plainly, never hide a slowdown, and publish frank after-action reports when serious bugs slip through.
4. **Evidence over claims:** a commit lands only with every gate recorded on that exact commit (`tools/land.py`); speed is measured on quiet native machines kept for timing, and a virtual machine's timing never decides a landing or a release; an AI auditor counts toward a release once its recall has been measured on a tree of ours with known defects.
5. **Clear boundaries:** support only the platforms we build and test natively, stop the build on any other with a message that names an alternative, and call a project supported from version 1.0.

---

BLAKE3-Servil, a fork of BLAKE3 1.8.7, aims at the fastest BLAKE3 in
every situation a program meets: alone, beside other work, beside other
hashing threads, natively and in virtual machines. It is two crates:
`blake3-servil-core`, which hashes on the thread that calls it, and
`blake3-servil`, which is the core with a pool of threads. This file holds what you need to change it and to cooperate
with its maintainers. Questions about BLAKE3 itself, or about the
official crate, belong upstream at
[BLAKE3-team/BLAKE3](https://github.com/BLAKE3-team/BLAKE3).

## Where things are

The README lists what BLAKE3-Servil adds for callers; the code is laid out so:

- `c/`: the assembly kernels the core builds. On AArch64, the integer +
  NEON hybrids (`blake3_neon_hybrid_aarch64.S`, generated by
  `tools/gen_neon_hybrid.py`) and the SME2 kernels; on x86-64, upstream's
  SSE4.1, AVX2, and AVX-512 kernels, and BLAKE3-Servil's own: the pass of whole
  chunks with a partial one (`blake3_partial_x86-64_*`, generated by
  `tools/gen_x86.py`) and the chunk root in one call
  (`blake3_chunk_root_x86-64_unix.S`, generated by
  `tools/gen_x86_chunk_root.py`). Every kernel a user runs is assembly.
- `src/`: the core, `blake3-servil-core` (the repository's root is its
  crate): the Rust around the kernels. It starts no thread and takes no
  lock; what its calls share is four one-byte atomics that record what
  startup found (the platform, the CPU's features, the self-test's
  state) and, with `std`, one thread-local store of scratch space.
  `convenience.rs` and `throughput.rs` (the two kinds of call,
  their contracts at the top), `incremental.rs` (the `Hasher`),
  `block.rs` (`Block` and `Batch`, the batch calls' input), `lib.rs`
  (what the calls share), `platform.rs` (detection and dispatch),
  `ffi_*.rs` (each kernel family's bindings), `pair.rs` (a whole chunk
  and a partial one side by side, x86-64), `many.rs` (batches),
  `each.rs` (collections, `update_each`), `io.rs` (`update_reader`),
  `self_test.rs` (the startup self-test), `hasher.rs` (the Hasher's
  stack, loop, and chunk state), and `tree.rs` (the tree walk).
- `threads/`: `blake3-servil`, the crate most programs use. It
  re-exports the core whole and adds the pool and a multithreaded form
  of each call: `lanes.rs` (the pool), `park.rs` and `finish.rs` (its
  handshakes), `lib.rs` (the calls). It hashes through the core's checked
  calls, and takes its scheduling and storage setup from
  `thread_support`, a hidden module of the core that changes with the
  two crates. `stream.rs` is the engine the Pipeline is to be built on
  (BLAKE3 #356), compiled for this crate's tests alone until then.
- `version/`: `blake3-servil-version`, the build's version string, in a
  crate of its own so that the kernels are not rebuilt for every edit.
- `b3sum/`: the CLI (`b3sums` on crates.io), on `blake3-servil`.
- `capi/`: the C API, `b3.h`, a thin layer over the core
  (`capi/src/lib.rs`), tested from Rust against the official test vectors
  and from C and C++ on Unix (`capi/tests/`).
- `tools/verify/`: the proofs (docs/quality-manual.md, "Proofs"); `tools/mutants/`:
  mutation testing and the list of mutants known to survive.

Each part's design, the measurements behind it, and the ideas tried and
set aside sit in its own documentation: the module's, the generator's
header, the tool's README.

## Build and test

The Rust library crates (`blake3-servil-core` and `blake3-servil`) assemble all
x86-64 and AArch64 (including NEON SHA-3 and SME2) kernels directly via
`rustc`'s `core::arch::global_asm!`, with zero third-party runtime or build
dependencies and no external C compiler required to assemble the libraries
(a platform linker is still needed for executables, and C/dev tooling such as
`capi/`, official `blake3` test oracles, and `tools/verify/` use a C compiler).
On AArch64 Linux and macOS every build includes both NEON and SME2 kernels and
selects SME2 at runtime on CPUs with 512-bit SME2.

The tests run under [cargo-nextest](https://nexte.st), each in its own
process (`cargo test` stops at once and says so); the doc examples run
under `cargo test --doc`. The C API tests also need cargo-c
0.10.26+cargo-0.100.0 and `pkg-config` on `PATH`; see
[`capi/README.md`](capi/README.md) for installation.

```sh
cargo nextest run --release --lib --tests          # the core
cargo test --release --doc
(cd threads && cargo nextest run --release)        # the crate with the pool
(cd threads && cargo test --release --doc)
(cd threads && cargo nextest run --release -P machine)   # the pool's shares timed with the machine to itself (pool_fairness)
cargo nextest run --release --manifest-path test_vectors/Cargo.toml
cargo nextest run --release --manifest-path capi/Cargo.toml   # the C API
sh tools/check-builds.sh            # the builds the suites leave out
(cd threads && RUSTFLAGS="--cfg shuttle" cargo test --release --test shuttle_finish --test shuttle_park)   # the pool's handshakes, every schedule a model checker tries
python3 tools/mutants/check.py        # the change since origin/next, each crate in turn, a minute; --whole for every mutant (an hour)
```

Each crate is built from its own folder: there is no workspace, so a
command at the root is the core's, and the same command in `threads/`
is the other crate's.

**While working, run the tests a change reaches:** `python3
tools/tests/reach.py check` compares the working tree with the last tree
it mapped and runs, through nextest, every test that ran a line the
change removes or rewrites, a test beside an insertion, a new test, and
every test when the change touches what line coverage cannot see (the
assembly, the build, the manifests, the nextest configuration, a
constant or a type or a `cfg`: anything the compiler, and no reading of
the text, decides the reach of). It prints each test's reason. A change
to a comment runs nothing; a change inside one function runs its tests,
a few seconds. `python3 tools/tests/test_reach.py` holds the rule's
controls, two of them Sam Shackleton's cases where a narrower rule hid a
failing test. `python3 tools/tests/reach.py map` records every test's
lines once (a minute); `check` keeps the map current from its own runs.
It replaces no suite above: the suites run before a landing; `reach`
makes the cycle between landings fast.

A change that makes a mutant survive, or lets a listed one be caught,
fails `tools/mutants/check.py`: add a test for the new survivor, or list
it in `tools/mutants/known-<arch>.txt` with the reason it survives (an
equivalent change, a choice between equally correct paths, another
machine's code; `--write` rewrites the list, each new row's reason
`UNCLASSIFIED` until you write one). The crate with the pool has lists
of its own, in `tools/mutants/threads/`, and `--crate threads` runs it
alone. A mutant whose tests the clock stops
(no test fails: a hang, or a wait that never ends) times out, an outcome
of its own, on `tools/mutants/timeouts-<arch>.txt` with its reason; the
check runs them every time, so one that a new test catches, or a change
in the code sets loose, is seen. A time-out is a bug the tests see only
by hanging: where a loop's variant or a wait's end can be asserted, make
it a failure instead (`CvStack::merge`, `update_turn`, `ensure_slow`
were made so), and the row goes.

A row whose reason claims speed alone ("speed", "equally correct
paths") is a claim a benchmark can test. `python3 tools/mutants/bench.py
[--since REV]` applies each surviving place alone and runs `bench-hashes
check` on it, about ten minutes a place. Slower: the path earns its
place. No cell runs it: a benchmark cell to write, or code to delete.
No cell slower, or faster: read it again at `--layouts 24`, then a
candidate to delete, or an improvement.

A survivor no test can kill is first a line to consider removing: an
unreachable branch goes (Task::run's batch branch did), and a pure
predicate gets a test of one thread even inside the pool (`visible`'s).
Where both paths are correct and one is faster, the reason says
`speed` and cites a measurement with the shortcut switched off
(`spare_lane`: 7935 B +29-53% without it). The handshake files
(`model files:` in the list: `finish.rs`, `park.rs`) are judged by
Shuttle's schedules as well as the suite, place by place: a mutant is
caught where either catches it. `check.py` narrows each mutant's tests
to those that ran its lines (`reach.py`'s map), gives each shard a
share of the CPUs, and caps each test process's memory, so a runaway
mutant cannot take the machine.

CI (`.github/workflows/ci.yml`) runs the suites on Linux x86-64 and arm64
(without SME2, and without SHA-3 under QEMU), and macOS's C API, for
every pull request, and by hand for a candidate that changes code for
those targets. A build for any other target (Windows, 32-bit,
big-endian, WebAssembly and the rest) stops with a message naming
official BLAKE3, which supports them, and
[#160](https://github.com/servil-software-factory/BLAKE3/issues/160) holds what full
support takes (dedicated hardware of ours to benchmark, optimize and
test on, then the kernels and the gates). The Mac runner
(`tools/runner/`) runs the Rust suites natively, on a Mac Mini M6. `sh tools/check-builds.sh`
runs, in minutes, the builds the suites above leave out: without std, on
one CPU without SME2, warnings as errors, and compile checks for x86-64.

The supported targets are 64-bit Arm (Linux, macOS) and x86-64 (Linux),
with the latest stable Rust (and any nightly feature BLAKE3-Servil chooses to
use). Official BLAKE3 serves the rest.

The generated kernels are committed beside their generators. Edit the
generator, then run it: `python3 tools/gen_neon_hybrid.py >
c/blake3_neon_hybrid_aarch64.S`, `python3 tools/gen_sme2_hybrid.py >
c/blake3_sme2_hybrid_aarch64.S`, `python3 tools/gen_x86.py >
c/blake3_partial_x86-64_unix.S`, or `python3 tools/gen_x86_chunk_root.py >
c/blake3_chunk_root_x86-64_unix.S`;
`tools/check-builds.sh` fails when a file and its generator drift apart.

## Performance

Speed is BLAKE3-Servil's purpose, so every change to `src/`, `threads/`, `c/`, `build.rs`,
`Cargo.toml`, or `Cargo.lock` passes a regression check first. The check
uses [bench-hashes](https://github.com/servil-software-factory/bench-hashes), in a
checkout of its own beside this one (neither inside the other), named
with `--fork`. From this checkout's root:

```sh
git clone https://github.com/servil-software-factory/bench-hashes ../bench-hashes
fork=$PWD
(cd ../bench-hashes && cargo run --release -- check --fork "$fork" --points "3 KiB,idle 3 KiB")   # choose the points the change can move
(cd ../bench-hashes && cargo run --release -- check --fork "$fork" --against OLD --cells all)  # every point, for a broad change
```

It builds the benchmark against both versions of BLAKE3-Servil and runs them
alternately on the same machine, so it needs no stored numbers. Its
exit status:

- 0: no cell slower;
- 1: a regression, its cells listed;
- 2: verdict pending: name a scope with `--points` or `--cells all`, or
  run on a quiet machine when other programs kept it busy.

`check` first prints the changed files and items; the author names the
points the change can move. `sh tools/install-git-hooks.sh` installs a
hook that presents that summary for code commits and keeps a pending
verdict pending. Once the explicit scoped check passes, commit with
`--no-verify` to use that result. To run the full benchmark against your
working tree, see bench-hashes' `CONTRIBUTING.md`.

The check runs its pairs in two stages: four pairs over the named cells,
then 64 pairs over the cells it suspects,
judged among themselves. Planted at one input length, it caught +20%
and +10%, not +6%, which cells after a gap drown in (bench-hashes #66).
Where a short-message cell turns on where a stack or a buffer happens to
sit (4 KiB aliasing, bench-hashes #65), one build's layout can decide
its verdict; Sam Shackleton's `tools/offset_check.py` (BLAKE3 #141)
measures that.

One machine's verdict covers that machine. A change to the pool or to a
kernel faces the many-core x86 machine (the EPYC) and the Mac before it
lands: removing the owed wakes passed the i7 and made the EPYC 4-12%
slower in 14 pool cells (BLAKE3 #119), and the i7 then found its fix
16-25% slower.

What a slower cell means for a change is a judgment in the service of
goals (Zooko, November 12, 2026). bench-hashes' `CONTRIBUTING.md` says
the same under "When a check reads a cell slower", with the questions
that find a cause quickly. The goals:

- **A user is never surprised by a slowdown we could have known.** A
  real one is fixed, or said plainly where users read (the changelog),
  with an owner.
- **We do not fool ourselves.** A reading the code did not cause is worth
  understanding far enough to stop it recurring.
- **Releases come soon.** An hour spent chasing a cell is weighed against
  what the chase can buy.

Whoever lands the change decides, and says why in a sentence where the
others read it (the commit message, the pull request). What bears on the
call: how large the reading is, whether it repeats by name, how many
machines agree, whether a user's call can reach the cell, what finding
out would cost, and what being wrong would cost. We own every slowdown:
one that lands does so with `--no-verify`, its slowed cells and their
numbers in its message, and an issue with an owner. When the call is
hard and the stakes are high, ask. A
streaming API's cells never slow to speed up another API. A commit in
`src/`, `threads/` or `c/` that leaves the machine code as it was (code for other
targets, tests, comments) skips the check with `--no-verify` and a line
in its message saying why. Commits made without the hook are checked
before they are pushed, each against its parent, and a run of them also
last against first, which sees slowdowns each step kept under the
margin.

## Branches and changes

Before opening a pull request or kicking the landing gates, run through
three quick authoring checks (and include the answer in the commit
message or pull request body where relevant):

1. **One truth and fewest modes:** Does this change keep two copies of
   one idea (two lockfiles, two readers, two formats) or add a mode that
   could be eliminated instead? Is anything now vestigial so it should
   be deleted in this same commit?
2. **Control proof (for non-Rust tools, CI steps, or new planted-fault
   controls where `cargo-mutants` does not run):** Temporarily disable
   the safeguard or plant the fault your new check guards against, run
   it, and record the observed failure.
3. **Non-default modes:** Exercise any `no_std`, optional-feature, or
   stamped-release branch your change touches rather than relying only
   on default/`+dev` runs.

`next` is the development line and `main` the release line. Work happens
on `candidate/<topic>` branches; a candidate joins `next` as a
fast-forward of its tip (so what was checked is what lands), by
`python3 tools/land.py land COMMIT` and no other push: each gate below
is a status on the commit (`land.py gate` runs this machine's and posts
them, `land.py record` posts one that ran elsewhere, `land.py status`
lists what is missing), and `next` accepts only a commit that `land.py`
found complete. A candidate lands once:

- every suite above passes, and `sh tools/check-builds.sh`;
- CI passes on it, started by hand (`workflow_dispatch`) when it changes
  code for targets the VM and Mac do not run (x86-64, AArch64 without
  SME2). Shared GitHub Actions runners run `blake3-servil` under
  `[profile.ci]` (`.config/nextest.toml`), which skips the 2-second
  wall-clock `two_callers_share_the_pool` ratio test that flaked under
  multi-tenant vCPU scheduling while keeping clockless fairness tests
  (`lanes::sources::test`) on every CI job and `pool_fairness` on our
  dedicated fleet hosts;
- mutation testing passes on fast native hosts for a change to the Rust
  (`python3 tools/mutants/check.py` on x86-64 Linux [~1.5 min] and Apple
  Silicon arm64+SME2 [~1.7 min]; `tools/mutants/cargo-nextest` runs fast
  `--lib` unit tests before `--tests` integration tests so mutants killed
  by unit tests fail in milliseconds instead of hanging behind blocking
  integration tests). Slow VM mutation runs (`arm-vm` `mutants aarch64`,
  which averaged 22.4 min/run and cost 7.1 hours across 19 Nov 23 runs
  with 8 timeout failures and 0 unique defects) are no longer a
  per-landing gate and remain available on demand for pre-release runs,
  while `arm-vm`'s Linux/AArch64 test suites (`tests aarch64`) stay a
  mandatory landing gate;
- its commit message says what it adds to the library or removes, with
  `python3 tools/size.py BASE REV`'s output where it changes the
  library's code (a few minutes: it counts and builds);
- when benchmarked library code changes (`src/`, `c/`, `build.rs`,
  `Cargo.toml`, `Cargo.lock`, `threads/src/`, `threads/build.rs`,
  `threads/Cargo.toml`, `threads/Cargo.lock`, `version/`), the regression
  check (`cells`) finds no slowdown natively on the timing Mac (a Mac
  Mini M6 that runs timing jobs alone), over every cell (`--cells all`:
  about twenty minutes there, queued in parallel with CI and tests).
  Changes outside benchmarked library code (`b3sum/`, `capi/`, tests,
  tools, CI, docs) do not require `cells` in `tools/land.py`. The Mac
  check is a job queued through the shared exchange
  (`tools/runner/README.md`, "Running a job"), and
  its result is a link on the pull request. Every cell, since a change
  checked at the points its author expected can slow one nobody named;
  a cell slower where the change means it to be (a call outside the
  pattern its API is tuned for) is recorded with its number in the
  commit message. Virtual machines are timed nightly on a best-effort
  basis (never awaited for a landing or a release, and a slowdown seen
  only on a VM is looked into when nothing better waits); the VM's
  correctness test suites on AArch64 Linux (`tests aarch64`) stay a gate.
- for a change to shipped code (the library crates, `b3sum`, the C
  header and API, and their build scripts and manifests), one review by
  an AI model of another family than its author's has read it, with
  `tools/review/BRIEF.md` as its brief (an author on a Claude model
  takes a GPT or a Gemini reviewer, and so on; where the author's model
  is not known, any model the author did not use). The reviewer works
  alone, builds and runs what it needs, and plants faults to see whether
  the change's tests catch them. Its report is public (a gist, or the
  pull request). **One round**, and a finding holds the landing **only**
  if it shows a wrong result, a crash or panic, a hang, or a slowdown.
  Everything else (comments, style, minor edge cases, extra tests) lands
  and becomes an issue. `python3 tools/land.py record review COMMIT
  success "REVIEWER: what it found; what was done; where the report
  is"` posts it. Tools, the job runner, mutation lists, workflows,
  integration-only tests, and docs do not need a landing review.
  (Zooko's Rule 2 trial, November 22, 2026: one ten-minute review of
  shipped code found the running-digest slowdown of BLAKE3 #472, while
  multi-round reviews of tools and mutation lists slowed down landings.
  Re-evaluated after a few landings for quality against calendar time.)

Whoever made the candidate lands it once every check has passed, the
same day: no person's review stands between a passing candidate and
`next`.

Every open issue and pull request has one assignee, the person whose
move is next. Finish your move, say in a comment what the next move is,
and assign the person who makes it. Close the item when nothing is left.
A workflow assigns the author to an item left with no assignee and asks
when there are several.

A change to a tool that runs for hours (`tools/mutants/check.py`,
`tools/verify/long-proofs.sh`, `bench-hashes regress` and `check`) lands
after a short run of it, start to finish, on each kind of machine that
runs it (the VM, the Mac, x86-64 Linux): a fault in its setup or
teardown otherwise costs a whole run, found at its end. For check.py
that run is `python3 tools/mutants/smoke.py`, about a minute.

Jobs of hours run on `next` overnight: the whole mutation run, and the
long proofs (`sh tools/verify/long-proofs.sh next`, which posts the
commit's "long proofs" status). The proofs' inputs are the kernels
(`c/`), the specification (`c2sp/`), the proof tools (`tools/verify/`)
and the checked generators. The script hashes these and the executing
driver's contents. A commit with matching inputs reuses a passed run
(`tmp/long-proofs/inputs/`); a Rust, build or page change never waits on
the proofs. Each run's logs stay in `tmp/long-proofs/COMMIT-INPUTS/`, so
another driver checking the same commit does not overwrite them. A failure there is fixed first, before the next change
to a kernel. After a candidate lands, bench-hashes pins its contender to
the new tip (`blake3-servil`'s `rev` in `Cargo.toml`, the full hash).
The instrument, `clocks`, is bench-hashes' own, so a result's bench
commit names it on both sides of a comparison. Pull requests are welcome against `next`; say in yours
which machines you measured on.

## Releases

A release is a commit everyone can stand behind: every check the
development line runs once per change, run once more on that commit, and
the pages users read rewritten for it. `main` takes it from `next`, and
only John and the organization's owners can update `main` (the
organization's ruleset). `python3 tools/release-check.py [COMMIT]`
reads each step's evidence. If the previous release was a patch on a
separate line, pass its published tag as `--previous TAG`. Use that same
tag for the comparisons below. The release's tracking issue lists what
it takes and ticks each step:

1. Once the code and API scope are settled, run `python3 tools/gen-ver.py
   X.Y.Z` from a clean release checkout. It stamps `X.Y.Z+<code parent's hash>`
   into both libraries, the version crate, their dependency pins, the CLI,
   the C library/header and CHANGELOG, and makes a version commit and **local** tag. The version's hash names the code parent; the
   tag names the version commit. cargo-c derives pkg-config's version from
   the C crate; the tool prints exact dependency lines for both libraries. Keep
   the tag unpublished while validating that commit; a branch at it makes
   it available to CI. Evidence is named by this version commit.
2. CI, every job, dispatched with `workflow_dispatch` on the exact candidate;
   `sh tools/check-builds.sh`. Pull-request CI normally checks a synthetic
   merge, so its head-SHA label alone is not evidence for the release commit.
3. `bench-hashes check --against <previous release tag> --cells all`,
   on the timing Mac (a Mac Mini M6, `mac-m6-timing` in the runners'
   exchange; `tools/release-check.py` reads that Mac's checks of the two
   commits: the one it started last decides, every one of them must be a
   whole record however old, and the job names both commits in full)
   and on the native x86 machines of the
   fleet; VM timing runs nightly on a best-effort basis and is not
   awaited for a release. Use one bench commit on both sides for the
   calls they share. Compare new calls with a suitable development
   baseline on the current bench. When the old API prevents one bench
   from building both sides, set `--old-bench <bench commit>` (the
   runner's `old_bench_commit`) and record the bench difference beside
   the result. The older bench must build beside BLAKE3-Servil, as every
   bench from 1f4dfd63 on does.
4. The long proofs, every kernel; the full mutation run.
5. The packages' dry-run (below), all four together: the core needs its
   version crate, the thread library needs the core, and the CLI needs the
   thread library, at versions crates.io does not have yet.
6. Deep security audits by at least two separate AI agents using different
   leading-edge models. Each starts independently and names the exact
   audited revision. Retain reports and finding dispositions with the
   release evidence; re-review affected code and the final version diff
   after changes. Resolve credible memory-safety, wrong-result and security
   findings before publishing. The [quality manual](docs/quality-manual.md#deep-security-audits-before-stable-releases)
   defines the scope, evidence and limits; AI review is not a human audit.
7. The pages, read as a newcomer would: the README's servil preface,
   `QUALITY.md` and `docs/quality-manual.md`, `CHANGELOG.md` (what
   changed for users, in their terms), the supported-platforms table
   (exactly what CI runs).
8. A full bench-hashes run on the version commit on the Mac, its results
   retained for publication with the release and named on the map.
9. Once the gates and reviews accept that exact version commit,
   move `main` to it, then publish its tag and artifacts (a release's
   commit is in `main`'s history, and the published check asks it):
   - the crates: publish all four from the same staged checkout and lock
     used for the dry-run, one at a time, each dependency first, stopping
     at the first that fails: `blake3-servil-version` (`version/`),
     `blake3-servil-core` (the repository root), `blake3-servil`
     (`threads/`), then `b3sums` (`b3sum/`; crates.io's `b3sum` is official
     BLAKE3's). Each is `cargo publish --locked --no-verify` with the
     dry-run's `--manifest-path` and `--target-dir` and the one `-p` name.
     (`--frozen` cannot publish: it forbids the request to the registry,
     as 0.10.0's first attempt found. The dry-run has built each package,
     and `python3 tools/release_artifacts.py TAG --published` then holds
     what crates.io serves to the commit.) The C package has
     `publish = false` and ships as libraries;
   - b3sum's binaries, built on each machine by `sh tools/b3sum-release.sh`
     from a fresh clone of the version commit (statically linked on Linux,
     the same bytes whoever builds them), each with its `.sha256` and `.b3`;
   - no archive of the C library: its build is not reproducible, so a
     published one could not be checked against the source as the other
     artifacts are. Users build it (`capi/README.md`);
   - the GitHub release, its text the CHANGELOG entry: made as a draft,
     every file attached, then published. Published, its files and its
     tag are frozen (the repository's immutable releases), so nothing is
     added or replaced afterwards.
10. The eBASH submission, pinned to the tag (`supercop/README.md`).

### The packages' dry-run, before any crate is published

From the version-stamped checkout:

```sh
sh tools/crates-release.sh
```

It packages the four crates together from a fresh clone of the version
commit, in a temporary parent workspace (the C package and test-vector
crate stay outside this publication), builds each packaged crate, and
copies the archives to `dist/`. Cargo resolves nothing while it does:
the dependencies are those of `tools/release/Cargo.lock`, fetched with
`--locked`, and the packaging runs `--frozen`. The CLI's packaged lock
names the checksums of those exact dependency archives.

Save its output to the commit-named release log and append
`publish-dry-run: ok` only when the command succeeds; this is a dry-run,
never permission to upload. The final publication runs from the directory
the script names, with `cargo publish --locked --no-verify` and the same
`-p` names, one at a time (step 9).

### The release lock

`tools/release/Cargo.lock` names every dependency the four crates are
packaged with. No release takes "the newest version today": a dependency
changes when a commit changes that file. (0.9.0's crates were packaged
with no lock, and its `b3sums` crate shipped dependency versions that no
test of ours had run, BLAKE3 #436.)

`b3sum/Cargo.lock` is what `b3sum` is built and tested with, and the
release lock holds each of its packages as it is there, plus the
libraries' test dependencies; `python3 tools/gen-ver.py --check` fails
where the two differ. To change a dependency: change it in `b3sum/`
(`cargo update -p NAME --precise VERSION`), commit, then
`sh tools/crates-release.sh --relock`, read the lock's change, and commit
it. The dependency policy's checks, below, then run on the new lock.

### The dependency policy

Both locked resolutions — all six repository crates in the workspace
(`tools/release/workspace.toml` and `tools/release/Cargo.lock`, covering
the four published crates plus `capi/` and `test_vectors/`) and the
standalone CLI (`b3sum/Cargo.lock`) — pass three checks in CI
(`dependency policy`), under every feature;
`python3 tools/dependency_policy.py` runs the same checks here. Every
Rust build and test in CI runs `--locked` against those two lockfiles
(`tools/ci-locked.sh` for the libraries, C API and test vectors;
`b3sum/Cargo.lock` for `b3sum`). That covers what a build compiles in,
what a build runs (build scripts, procedural macros), and the locked
test dependencies of both graphs.

- **Ours or from crates.io.** A package that a manifest takes by path
  must be one of the six repository crates, which
  `tools/release/workspace.toml` names. The two tools below take any
  such package for ours, so a library copied into the repository would
  pass them unaudited.
- **`cargo-deny`, against `deny.toml`.** No advisory in RustSec's
  database, wherever the package is in the graph. No yanked version,
  and a version whose yank status could not be read fails too.
  crates.io as the one source. A licence of MIT, Apache-2.0 or
  TGPPL-1.0 (BOSL-1.0 is welcome too; since SPDX has no identifier for
  it, a crate under it needs both a `clarify` entry identifying its
  licence text as `LicenseRef-BOSL-1.0` and an `allow` or `exceptions`
  entry for `LicenseRef-BOSL-1.0`); the one exception (`unicode-ident`,
  `Unicode-3.0`) is recorded there with its reason.
- **`cargo-vet`, against `tools/release/supply-chain/`.** Every version
  has an audit published by Mozilla, Google, the Bytecode Alliance,
  Zcash, Embark or ISRG, or an exemption recorded in `config.toml`:
  `safe-to-run` for a package that only tests use, `safe-to-deploy` for
  any other. The exemptions are a list to shorten, one audit at a time.

CI fetches both tools by their hashes, checks that `b3sum/Cargo.lock`
and `tools/release/Cargo.lock` agree (`tools/gen-ver.py --check`), and
runs ten planted-fault controls (`python3 tools/dependency_policy.py
controls`) beside the checks.

A commit that changes a dependency runs the checks. For a new version
without a published audit, read what changed and record the audit
(`python3 tools/dependency_policy.py vet diff NAME OLD NEW`, then `vet
certify NAME OLD NEW`), or add an exemption (`vet add-exemption NAME
VERSION`) and give the reason in the commit.

- SUPERCOP's non-Cargo C packaging is outside the Rust lockfiles.

### Every artifact is a clean build of the version commit

Before anything is published, the release's artifacts are gathered in the
version-stamped checkout's `dist/`: the crates' archives (the dry-run
above writes them) and b3sum from each machine's own `dist/`.
`tools/release-check.py` passes only when each is a clean build of the
version commit, by `python3 tools/release_artifacts.py TAG FILE...`: a
program by the build version it holds, a crate file by file against the
commit. Once the release is published, the `release artifacts` workflow
checks what users download the same way, as anyone can:
`python3 tools/release_artifacts.py TAG --published`. (0.9.0's two b3sum
binaries were built in checkouts that held untracked files and say
"dirty", BLAKE3 #435: that command fails on them.)

The tag's name is the release's source: the 40 hex digits in it, which
`b3sum --version` prints too, are the code commit's hash, and the check
holds the version commit to that commit with the version written in and
nothing else (`tools/gen-ver.py` makes it so). A moved tag, or a version
commit that carries anything more, is no release to it. Release tags
cannot be moved or deleted on GitHub either (the `release tags` ruleset,
which no one bypasses). Take the checker from the code commit or from
`main`, not from the tag's own commit.

A program's build version is its own word, which shows a mistake and
not a forgery. So b3sum's Linux binary is also built reproducibly:
`tools/b3sum-release.sh` gives the same bytes on any machine from the
same commit, with the compiler and C library that
`tools/b3sum-release.toolchain` names (the script stops on any other).
The crates' archives are reproducible too, given the release lock and the
same Cargo: `tools/crates-release.sh` gives the same bytes wherever it
runs, the files Cargo writes into an archive (its `Cargo.toml`, its
lock) included.
Two builders must agree before a release: `release-check.py` passes only
when each binary and each crate in `dist/` is, byte for byte, the one
GitHub's machines made in the commit's CI run (the `b3sum release build`
jobs). After the release, the `release artifacts` workflow makes them
again from the tag and compares what was published, and so can anyone
with Docker or Podman:

```sh
git checkout TAG
docker run --rm -v "$PWD":/src -w /src "$(sed -n 's/^image //p' tools/b3sum-release.toolchain)" sh tools/b3sum-release-container.sh
python3 tools/release_artifacts.py TAG --published --rebuilt dist
```

The C library's archive is not rebuilt so: it is checked by its build
version alone (BLAKE3 #436).
